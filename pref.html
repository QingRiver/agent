01设计原则

P1状态转移是任务的核心实体

op 只是转移的触发器。一个转移 = guard → local → propagate 三段，本体集中在转移声明内，不散落在手写函数里。

P2转移要么发生要么抛错

guard 不通过、from 不匹配，一律抛 TransitionError。没有 'noop'、没有 allowed: false 的静默路径。幂等责任上移到调用方，转移本身对所有 action 一视同仁。

P3联动与树同构

状态副作用沿 parent 链向上传播，机制复用树的拓扑。propagateUp(taskId, effect) 遍历 ancestors(tree, taskId)——传播路径就是树遍历路径。cascade 不是独立的 plan 层，是转移执行后的传播步骤本身。

02包结构

目录从 9 个压到 1 个根下 8 文件。视图层（perspective / filter / forecast / fixtures / prompts）拆到 @agent/gtd-view 独立包。

03数据模型与聚合根

TaskData：一字段一戳

现有 status + completedAt + heldAt + droppedAt 三个互斥戳是派生值被当成了存储值，靠 match.exhaustive() 维护一致性。重写后只存 status 与一个 statusChangedAt——status 已表达终态，戳只需一个。

GtdModel：唯一聚合根

取代现有三套等价 API（自由函数 liveTasks/findLive/taskTree + RowStore 类 + GtdReader 类）。读写都通过它。

model.ts
export class GtdModel {
  private readonly rows: EntityRow[]
  private treeCache: TaskTree | null = null
  private counter: number

  constructor(rows: EntityRow[] = []) {
    this.rows = rows
    this.counter = maxSyncId(rows)
  }

  // —— 读 ——
  liveTasks(): TaskRow[] { /* filter !deleted && entity==='task' */ }
  findTask(id: string): TaskRow | undefined { /* live task by id */ }
  tree(): TaskTree {
    if (!this.treeCache) this.treeCache = buildTaskTree(this.liveTasks())
    return this.treeCache
  }
  ancestors(taskId: string): TaskRow[] { return ancestors(this.tree(), taskId) }
  effectiveStatus(taskId: string): ExplicitStatus | undefined { /* effectiveStatus(task, tree) */ }
  availableActions(taskId: string): StatusAction[] { /* 见 §05 */ }

  // —— 写（转移内部调用，不对外）——
  setStatus(task: TaskRow, status: ExplicitStatus, ts: string): void {
    task.data.status = status
    task.data.statusChangedAt = ts          // 两行，删掉三戳的 exhaustive match
    task.data.updatedAt = ts
    task.syncId = ++this.counter
    this.invalidate()
  }
  invalidate(): void { this.treeCache = null }

  allRows(): readonly EntityRow[] { return this.rows }
}

04状态转移表

转移是显式注册的实体。表的值是"完整三段"（guard / local / propagate），不是现在 TransitionEdge 只描述 to + 外部 cascade 函数。from 允许联合——delete 从三态都可，不需重复定义 DELETE_EDGE。

对称性落在数据上：完成/搁置/删除父「不改子自身状态」用无 propagate 表达；重开/恢复/移出回收站「向上翻」用有 propagate 表达。不再需要 planCompleteCascade/planDropCascade 恒 [] 的死代码占位。

transition.ts — TRANSITIONS 全表
export interface TransitionSpec<I = void> {
  action: StatusAction
  from: ExplicitStatus | ExplicitStatus[]
  to: ExplicitStatus
  guard?: (task: TaskRow, input: I) => void      // 不通过即 throw TransitionError
  local?: (task: TaskRow, input: I, ctx: Ctx) => void  // 改自身 + 重复克隆等
  propagate?: UpEffect                          // 沿父链向上传播
}

export const TRANSITIONS: Record<StatusAction, TransitionSpec> = {
  // 完成子不上向 → 无 propagate
  complete: {
    action: 'complete', from: ACTIVE, to: COMPLETED,
    local: (task, cmd, ctx) => cloneIfRepeating(task, cmd, ctx),
  },

  // 搁置子不上向 → 无 propagate
  drop: {
    action: 'drop', from: ACTIVE, to: HOLD,
  },

  // 重复任务不允许重开：guard 抛错
  reopen: {
    action: 'reopen', from: COMPLETED, to: ACTIVE,
    guard: task => {
      if (task.data.repeatRuleId != null)
        throw new TransitionError('repeat_not_reopenable', task.id, `重复任务不可重开，下一实例已生成`)
    },
    propagate: { kind: 'descendant-activated' },
  },

  restore: {
    action: 'restore', from: HOLD, to: ACTIVE,
    propagate: { kind: 'descendant-activated' },
  },

  // 从 active/completed/hold 三态都可；已 deleted 再 delete 抛 invalid_from
  delete: {
    action: 'delete', from: [ACTIVE, COMPLETED, HOLD], to: DELETED,
  },

  restoreFromTrash: {
    action: 'restore_from_trash', from: DELETED, to: ACTIVE,
    propagate: { kind: 'descendant-activated' },
  },
}

读侧 availableActions：从同一张表派生

transition.ts
export function availableActions(task: TaskRow): StatusAction[] {
  return (Object.values(TRANSITIONS) as TransitionSpec[])
    .filter(spec => matchesFrom(spec, task.data.status))
    .filter(spec => !wouldReject(spec, task))      // 跑 guard 但吞错（读侧不抛）
    .map(spec => spec.action)
}

function matchesFrom(spec: TransitionSpec, status: ExplicitStatus): boolean {
  return Array.isArray(spec.from) ? spec.from.includes(status) : spec.from === status
}

读侧（菜单）与写侧（runner）共享同一张 TRANSITIONS 表的 from / guard，不会漂移。UI 先用读侧过滤菜单、漏过滤时写侧抛错兜底。

05转移执行器

runner 是表驱动的薄分发——查表、校验 from、跑 guard、改自身、跑 local、向上传播。所有状态动作共用这一条路径；complete 不再特殊手写。

transition.ts — transition() runner
export function transition(
  model: GtdModel,
  taskId: string,
  action: StatusAction,
  input?: unknown,
  ts: string = nowIso(),
): void {
  const task = model.findTask(taskId)
  if (!task) throw new TransitionError('not_found', taskId, '任务不存在')

  const spec = TRANSITIONS[action]

  // from 校验：不在 from 集合 → 抛错（不是 noop）
  if (!matchesFrom(spec, task.data.status))
    throw new TransitionError(
      'invalid_from', taskId,
      `${action} 要求 ${fmtFrom(spec.from)}，当前 ${task.data.status}`,
    )

  // guard：不通过 → 抛 TransitionError
  spec.guard?.(task, input)

  // local：改自身 + 重复克隆等
  model.setStatus(task, spec.to, ts)
  spec.local?.(task, input, { model, ts })

  // propagate：沿父链向上传播副作用
  if (spec.propagate) propagateUp(model, taskId, spec.propagate, ts)
}

06错误模型

转移失败一律抛 TransitionError，调用方靠 error.code 显示拒绝文案。删掉 'applied' | 'noop' 返回值。

transition.ts
export type TransitionErrorCode =
  | 'not_found'
  | 'invalid_from'            // 已在目标态再触发（如 delete 一个已删除项）
  | 'repeat_not_reopenable'   // 重复任务的 complete 已生成后继，不可 reopen
  | 'parent_not_found'
  | 'cycle'                   // move 到自己子树下
  | 'inbox_no_children'      // 收件箱任务不能有子任务

export class TransitionError extends Error {
  constructor(
    readonly code: TransitionErrorCode,
    readonly taskId: string,
    message: string,
  ) { super(message); this.name = 'TransitionError' }
}

幂等责任上移到调用方。若有「批量清理回收站」这类确实需要幂等的场景，由 op 层显式判断 if (task.status !== 'deleted') transition(...)，转移本身不吞重复操作。转移对所有 action 一视同仁：from 不匹配就抛错。

07向上传播：与树同构

这是设计的核心机制。传播函数复用树的 parent 链——结构即机制。从 taskId 出发沿 ancestors(tree, taskId) 向上，每层根据 effect 决定是否变更、是否继续传播。

tree.ts — propagateUp + decide
// 可扩展：未来加新联动类型只需加一个 variant + 一个 decide 分支，骨架不动
export type UpEffect =
  | { kind: 'descendant-activated' }   // 后代变活跃 → 拉回已完成祖先
// | { kind: 'descendant-blocked' }    ← 未来扩展占位

type Decision = 'stop' | 'continue' | 'flip'

// 纯函数表：每层祖先如何对待向上传来的 effect
function decide(task: TaskRow, effect: UpEffect): Decision {
  switch (effect.kind) {
    case 'descendant-activated':
      // 搁置/删除最优先：被这类祖先挡住，传播终止（不解除祖先的搁置/删除）
      if (task.data.status === HOLD || task.data.status === DELETED) return 'stop'
      // 已完成祖先 → 拉回活跃，继续向上
      if (task.data.status === COMPLETED) return 'flip'
      // 活跃祖先 → 穿过，继续向上
      return 'continue'
  }
}

export function propagateUp(
  model: GtdModel,
  fromTaskId: string,
  effect: UpEffect,
  ts: string,
): void {
  // 沿 parent 链 —— 和 ancestors(tree, taskId) 同一原语
  for (const ancestor of model.ancestors(fromTaskId)) {
    switch (decide(ancestor, effect)) {
      case 'stop':    return                       // 被挡住，传播终止
      case 'flip':    model.setStatus(ancestor, ACTIVE, ts)  // 拉回，继续向上
      case 'continue': /* 不改，继续向上 */ break
    }
  }
}

这就是现有 planUpwardActivation 的语义，但：不再产 CascadeStep[] 中间表示（plan 层消失）；不再 applySteps 二阶段执行；传播骨架与 effect 解耦。

create / move 不是状态转移，但活跃任务被建/移到已完成父下时同样要拉回祖先——它们直接调 propagateUp，走同一条传播路径：

ops.ts — create / move 复用传播
export function createTask(model: GtdModel, cmd: CreateCmd): void {
  // …校验 parentId 存在、push 新行（status=ACTIVE）…
  model.setStatus(newTask, ACTIVE, cmd.clientTs)
  propagateUp(model, cmd.taskId, { kind: 'descendant-activated' }, cmd.clientTs)
}

export function moveTask(model: GtdModel, cmd: MoveCmd): void {
  // …校验无环、改 parentId + order…
  if (task.data.status === ACTIVE)
    propagateUp(model, cmd.taskId, { kind: 'descendant-activated' }, cmd.clientTs)
}

08effective 派生（只读）

完成/搁置/删除父不改子自身状态——子的有效态靠只读派生跟随。向下不传播显式状态变更，用「向下无 propagate、effective 只读派生」天然表达，不再需要 cascade 注释解释四句口诀。

tree.ts — effective 派生
// 有效状态：祖先链折叠。删除最优先；否则根→本任务第一个 hold/completed 决定。
export function effectiveStatus(task: TaskRow, tree: TaskTree): ExplicitStatus {
  if (task.data.status === DELETED) return DELETED
  const path = [...ancestors(tree, task.id)].reverse()  // 根→父
  path.push(task)
  for (const node of path) {
    if (node.data.status === DELETED) return DELETED
    if (node.data.status === HOLD || node.data.status === COMPLETED) return node.data.status
  }
  return ACTIVE
}

// effective due = 天花板：min(自身 dueDate, 祖先 effectiveDue)
export function effectiveDue(task: TaskRow, tree: TaskTree): string | null { /* minIso 沿链折叠 */ }

// effective defer = 地板：max 沿链，再钳 min(it, effectiveDue)
export function effectiveDefer(task: TaskRow, tree: TaskTree): string | null { /* maxIso 沿链折叠 */ }

09availability

建立在 effectiveStatus 之上，不再递归遍历祖先 availability——effectiveStatus 已折叠祖先链。删掉现有 visiting / cache / 环路检测那套（effectiveStatus 无递归、无环风险）。

availability.ts
export function computeAvailability(
  task: TaskRow, model: GtdModel, now: Date, dueSoonMs: number,
): ComputedStatus {
  // effective 已折叠祖先链：非 active 即阻塞（终态/被祖先压）
  const eff = model.effectiveStatus(task.id) ?? ACTIVE
  if (eff !== ACTIVE) return BLOCKED

  // 墙钟未解锁
  if (!isUnlocked(effectiveDefer(task, model.tree()), now)) return BLOCKED

  // 兄弟 sequential：前序活跃兄弟阻塞后置
  if (isSequentiallyBlocked(task, model)) return BLOCKED

  // 截止日
  return dueState(effectiveDue(task, model.tree()), now, dueSoonMs)
}

10重复克隆（local 副作用）

克隆是 complete 转移的 local 副作用，不再让 completeTask 绕开 runner 手写一套。后继 id 由规则 id + 次数决定（确定性），客户端提议值忽略。

repeat.ts — cloneIfRepeating
export function cloneIfRepeating(task: TaskRow, cmd: CompleteCmd, ctx: Ctx): void {
  const rule = task.data.repeatRule
  if (!rule || shouldStop(rule, new Date(cmd.clientTs))) return

  const nextTaskId = successorId(rule.id, rule.completedOccurrences + 1)
  // 已克隆过（幂等）/ 占用冲突 / 复活软删同源行
  const placement = placementForNextTaskId(task.id, nextTaskId, ctx.model)
  if (placement === 'already-live') return

  task.data.repeatRule = { ...rule, completedOccurrences: rule.completedOccurrences + 1 }
  cloneNextInstance(task, rule, nextTaskId, placement, cmd.clientTs, ctx)

  // 新实例是活跃任务，挂到已完成父下 → 拉回祖先
  propagateUp(ctx.model, nextTaskId, { kind: 'descendant-activated' }, cmd.clientTs)
}

11op 层：薄触发器

op 是「算出要触发哪些 transition + 哪些 patch，按序调用」的编排，不再产 GtdIntent[] 中间表示——直接在 model 上调 transition() / patch()。多意图批次（indent = move + 复制标签 + 设 groupType）在此编排。

ops.ts — 编排示例
// 单转移：直接薄触发
export function planComplete(model: GtdModel, taskId: string): void {
  transition(model, taskId, 'complete')
}

// 多步骤批次：indent = move + upsert updatedAt + 复制父标签 + 设父 groupType
export function planIndent(model: GtdModel, taskId: string): void {
  const task = mustFind(model, taskId)
  const prev = previousSibling(model, task) ?? throw new TransitionError('no_sibling', taskId, '前面没有可作为父级的任务')
  // 1. 移到 prev 下（move 内部已含 propagateUp）
  moveTask(model, { taskId, parentId: prev.id, order: nextOrderUnder(model, prev.id) })
  // 2. 复制父标签
  copyTagsFromParent(model, taskId, prev.id)
  // 3. 父无 groupType 则设 parallel
  if (!prev.data.groupType) patch(model, prev.id, { groupType: 'parallel' })
}

12apply 与 purge

op 层直接在 model 上操作，apply 只剩「批量 + purge + 序列化往返」。服务端权威执行与客户端乐观预览共用同一套 op。

apply.ts
export type Op =
  | { kind: 'transition'; taskId: string; action: StatusAction }
  | { kind: 'create'; cmd: CreateCmd }
  | { kind: 'move'; cmd: MoveCmd }
  | { kind: 'patch'; entity: GtdEntity; id: string; patch: Partial<EntityDataOf<GtdEntity>> }
  | { kind: 'purge'; taskId: string }

export function applyOps(rows: EntityRow[], ops: Op[], userId: string): EntityRow[] {
  const model = new GtdModel(structuredClone(rows))
  for (const op of ops) runOp(model, op, userId)
  return model.allRows().filter(r => r.entity === 'task' || !r.deleted)
}

// purge：一处。delete(T) 不改子自身状态，子靠 effective 跟随进回收站视图；
// 若只 purge(T)，子失去删除祖先覆盖会「复活」——故 purge 连带物理删除整个子树。
function purgeTaskTree(model: GtdModel, taskId: string): void {
  const task = model.findTask(taskId) ?? throw new TransitionError('not_found', taskId, '任务不存在')
  if (task.data.status !== DELETED)
    throw new TransitionError('invalid_from', taskId, '不在回收站中，不能永久删除')
  const ids = new Set([taskId, ...subtree(model.tree(), taskId).map(t => t.id)])
  removeFromRows(model, ids)   // 含挂在其上的 task_tag / attachment
}

Op 取代现有 GtdCommand(8) + GtdMutation(8) + GtdIntent(3) 三层包装。task 的 status / parentId 不可走 patch（约束写在 runOp 里：patch 命中 task 且含这两字段即抛错），不再靠 schema omit + 注释维持。

15迁移要点
